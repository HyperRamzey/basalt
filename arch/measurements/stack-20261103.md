## the knob: `--resident-headroom-slack-gib N`

`resident-experts` sizes its RAM copy from the RAM above a safety headroom:
`max(--resident-headroom, ram_margin() + what loads after the copy + what --serve takes while serving)`.
The flag takes `N` GiB off that headroom, once, at the three places it is spent
(`auto_plan`'s `fits()`/`floor_for()`, the loader's copy limit in `resident_load.cpp`, the estimate in
`cache_fill.cpp`), with `platform::ram_margin()` kept as the floor because
`FileExpertSource::pin_cache_complement` applies it too. So: a run without `--serve`, whose headroom
is the margin alone, is unchanged; a slack past the headroom the plan computed comes out of the OS
file cache's floor, never the margin; and the runtime RAM guard keeps the floor it always had — only
the copy grows. Default 0. `tests/program/auto_plan_test.cpp` covers it (`auto_plan_test: ok`).

Config: `engine.resident-headroom-slack-gib: 2`, and `engine.prompt-cache: 3 -> 2` (a checkpoint is
~118 MiB of RAM the copy cannot use; the tuning round found 6 and 3 equal on reuse, so 2 gives the
RAM back).

Startup on this box after the change (`~/.cache/basalt/9d857ba6311ace55/engine.log`):

```
RAM floor 8.3 GiB (2.7 margin + 5.6 cache), 37.5 GiB experts on SSD, RAM copy <= 30.6 of 39.7 GiB
FileExpertSource: RAM room for the complement: 30.47 GiB (39.73 GiB available minus 9 GiB headroom and the page overhead)
resident RAM mode: 30.47 GiB of experts in RAM (page-locked), 1229 in the GPU cache
```

The headroom term is 9 GiB where the previous run printed 11. The copy is bounded by the RAM free at
plan time — that run had ~41.7 GiB free and pinned 30.68, this one 39.73 and pinned 30.47 — so what
the flag provably changes is the reservation, and at equal free RAM it moves ~2 GiB of the complement
from SSD reads into RAM. 37.2 GiB (52 %) still lives only in the file, which is why the engine still
warns about decode reading the SSD. No t/s measurement was taken for this change.

The `fallback: glue off for the layer's experts (types 12 / 7)`, `(13 / 8)` and `(12 / 8)` lines are
expected and unchanged: `dec_moe_glue_ok()` (`src/kernels/cuda/dec_moe.cuh`) fuses gate/up types
16/17/18/21/22/42 (40 for NVFP4) only, and this pack's layers are Q4_K/Q5_K with Q5_1/Q8_0 downs, so
those layers take the unfused MoE path. Upstream main has the same gate.

## packaging fix

`refresh-stack.sh` now diffs with `git diff --binary`. Without it the stack's binary expert profile
(`data/profiles/qwen4exp-48x512.prof`, in the stack since the `.basalt` version 2 step) was written
as the stub line `Binary files ... differ`, which `git apply` refuses ("cannot apply binary patch
without full index line") — so neither the refresh check nor `PKGBUILD prepare()` could reproduce the
stack from a clean clone; the patch path has been broken since the 0.2.0 series. The refresh now
prints `verified: clean upstream clone + basalt-stack.patch -> tree ef5076fd…`.

Two build notes for this machine: `makepkg` runs git with `GIT_CONFIG_GLOBAL=/dev/null`, so the dev
clone at `packaging/src/basalt` needs a **local** `user.email`/`user.name` or the `_stack=` merge in
`prepare()` dies with "unable to auto-detect email address"; and `pkgver()` only reads
`patches/VERSION` in patch mode, so a `_stack=` build is labelled from the merge commit
(`0.1.0.r2329.g130c259a`, which pacman reads as a downgrade) while building the same verified tree.
Patch-mode builds also need a clean `$srcdir/build`: its CMake cache remembers which source directory
configured it, and the patch mode builds in `$srcdir/stack`.
